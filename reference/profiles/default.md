# Default profile

Used when a source doesn't name a more specific profile.

**A profile is a thin overlay, not a second rulebook.** The card craft — `card-rules.md`,
`editor-checklist.md`, `card-recipes.md` §2–11, the Cold-Solve Gate, the regression
library — is subject-independent and applies to every source unchanged. A profile only
answers three questions the universal rules deliberately leave open:

1. **What is this material FOR?** (the test or the performance it feeds)
2. **Which archetypes should dominate?** (the mix, from `card-recipes.md`)
3. **Any subject-specific traps?**

If a profile ever seems to contradict `card-rules.md`, the rules win — except where
`parker-preferences.md` overrides both.

---

## 1. What it's for
General knowledge Parker chose to keep. There's no specific exam shaping it, so optimize
for **durable, honest recall**: he should be able to produce the fact cold, years later,
in a shuffled deck full of unrelated subjects.

## 2. Archetype mix
No forced bias. Pick the archetype that genuinely fits each highlight (`card-recipes.md`
§1 decision table). In practice this lands near:

- ~40% definitions and term↔meaning bindings (two-way by default)
- ~20% lists / enumerations / classifications
- ~15% mechanisms, causes, sequences
- ~15% numbers, values, thresholds
- ~10% comparisons and exceptions

Let the source decide. A dense conceptual chapter is mostly mechanism; a glossary chapter
is mostly definitions. Don't manufacture scenario cards for material that has no
scenarios.

## 3. Traps
- **Don't over-card a book Parker is reading for interest** rather than for a test. The
  yellow mark still means "I want this," so never drop it (Rule 0) — but prefer one
  excellent card over three thin ones.
- **Prereq closure matters more here**, because there's no course scaffolding around the
  card. If a term needs a neighbor term to make sense, fold in the one-clause definition
  or make the sibling card (card-rules #11).
